## 3. 원인 구분

### A. 평가 문자열 규칙의 한계 — 후처리 점수 변경 금지

`scoring_l302.py`는 승인 시점에 고정된 capability 표현 목록과 intent 부분문자열 일치 기준을 사용한다. 이 규칙이 영어 동사나 `meeting.schedule`, `output.echo` 같은 동등한 표현을 허용하지 않아 **의미상 맞는 일부 모델 결과를 실패 처리했을 가능성**이 있다.

하지만 이번 로그를 본 뒤 목록을 추가해 같은 실험의 40%를 상향 재계산하는 것은 사후 기준 변경이므로 **금지**. 채점 기준 개선이 필요하다면 새로운 버전, 변경 사유, 담당자 사전승인, 새로운 측정의 증적을 별도로 관리해야 한다.

### B. 실제 Analyzer 출력 계약 위반 / 불안정

현재 `RequestAnalyzerService._SECURITY_SYSTEM_CONTRACT`는 이미 lower_snake_case 엔터티, USER_EXPLICIT, 사업 기능과 Tool 이름 구분, 누락 입력/명확화 일관성 등을 규정하고 있다. 그럼에도 모델은 일부 요청에서 엔터티 이름·누락, 업무 기능 누락 및 스키마 검증 실패를 보였다.

**범용적 개선 후보**: (1) 한국어 지시의 intent 및 필수 업무 기능 추출 일관성, (2) 실체 엔터티 이름의 영문 표준화와 명시적 텍스트 보존, (3) JSON 검증 실패의 비민감 진단 정보 제공, (4) 구조 검증/수정 재시도 시 안전성·지연·실패 건수 정책 검토.

1. **기준선 보존:** 최초 `NOT_MET 40.0%`와 원본 SHA-256을 별도 보관. 작업 중 원본 JSON 수정 금지.
2. **원인별 개발 티켓 또는 PR:** 승인 gold/scoring 변경과 운영 Analyzer 변경을 **분리**하고, 수정 이유를 업무 품질 기준으로 작성. 관측 사례의 문자열을 외워서 맞추는 고정 규칙 금지.
3. **C03 재현 진단:** 스키마 오류 `loc`/`type`만 수집하는 비민감 진단 기법 도입. 실제 모델 응답이나 인증정보를 감사자료·GitHub에 남기지 않음.
4. **운영 개선:** 계약/모델 출력 안정성 향상은 비평가 사용자 지시를 포함한 일반 회귀 테스트로 검증. 운영 API·DB 권한·Tool 호출 흐름 보호.
5. **평가기 개선이 필요한 경우:** 새로운 scoring 버전과 독립적인 검토·승인 절차 필요. 기존 v1 공식 40% 결과 유지.

7. **최종 보고:** 최초 미달 → 분석 → 변경 Git/CI → 새로운 측정 → 개선효과를 구분하여 추적. 달성 여부는 해당 승인 기준 및 측정 범위에 한정해 기술.
